# Statement data integrity and deployment notes

## 1. Rebuilding the statement history (old data)

Rows imported before the canonical ingestion pipeline have no `fingerprint`.
They may carry a wrong direction (the old CSV parser read every CREDIT as
DEBIT), invented timestamps and raw statement text, and the old bootstrap
built payee edges from them. `scripts/rebuild_statement_history.py`
separates them so that there is one authoritative history.

Stop the backend first. The script is a **dry run unless `--apply` is given**.

```bash
# See what would change (read-only - opens the database in read-only mode)
python scripts/rebuild_statement_history.py

# Real database: back up, quarantine, rebuild, re-import retained statements
python scripts/rebuild_statement_history.py --apply --reimport-retained

# Development / demo database: the same, plus the synthetic demo payee crowd
python scripts/rebuild_statement_history.py --apply --reimport-retained --reseed-demo

# Import one more file for a known user
python scripts/rebuild_statement_history.py --apply --import path/to/file.csv --user usr_xxxx
```

| Step | What happens | Reversible? |
|---|---|---|
| Backup | `data/backups/<db>.<timestamp>.db` (SQLite backup API) + JSON manifest of counts | this is the undo |
| Quarantine | fingerprint-less rows are **moved** to `statement_transactions_legacy` (never read by the app); `--purge-raw-text` clears `raw_line` there | yes (rows kept) |
| Observations | `STATEMENT_OBSERVED` ledger rows removed and re-derived from canonical rows | yes (re-derived) |
| Stale payees | payees with any statement-derived edge get their `payee_reputation`/`payee_payers` rows rebuilt; report counts and block flags restored | backup |
| Preserved | `SYSTEM_CONFIRMED` / `OTHER_OBSERVED` ledger rows; payees touched only by demo seeds or non-statement users (left byte-for-byte); users, scored transactions, reports | - |
| Mixed payees | a payee with both a statement-derived edge and an un-ledgered edge from someone else cannot be split exactly: the script **refuses** unless `--drop-mixed-legacy` | - |
| Graph | `payee_graph_cache` / `graph_components` rebuilt from remaining edges | - |
| Re-import | `--reimport-retained` runs `data/uploaded_statements/<owner>_stmt_<id>_<name>` through the canonical pipeline (idempotent) | - |
| Profiles | rebuilt from canonical rows; users left with none keep the old profile unless `--reset-orphan-profiles` (listed either way) | backup |

Running the script twice changes nothing the second time.

## 2. Cross-source duplicates

Stage 1 - fingerprint (same kind of source): transaction ID when present,
otherwise time + amount + direction + UPI ID (+ name only without a UPI ID)
+ occurrence index. Re-uploading a file is a no-op; two identical rows in one
file stay two payments.

Stage 2 - cross-source match against the user's rows from OTHER statements
(`backend/app/ingestion/dedupe.py`). A match needs all of:

1. same user, same known direction, same amount to the paisa;
2. same payee - equal UPI IDs when both have one, otherwise equal normalised
   names; a name never matches a different UPI ID;
3. no contradicting reference IDs (two same-shaped IDs that differ = two
   payments; different ID schemes, e.g. PhonePe `T...` vs a 12-digit UTR, are
   not compared);
4. time: **STRONG** - equal reference IDs, or both rows timed and within
   2 minutes; **DATE** - one row date-only, same IST date, and the match is
   unique (one stored candidate, one incoming row). Otherwise **AMBIGUOUS**:
   both kept and reported (`ambiguous_cross_source_kept`);
5. one-to-one within an import; rows without a timestamp are never merged.

## 3. Time zone

All statement and decision times are **IST wall time, stored naive**
(`backend/app/core/clock.py`). Naive statement times are taken as IST and
never shifted; aware times are converted to IST; "now" is IST derived from
UTC, so a Render server in UTC and a laptop in IST make the same decision.
First/last payment, days since payment, hour-of-day (hours from usual),
seconds since last transaction, payments in the last hour and payments today
all read the same convention: serving code normalises timestamps with `clock.app_iso` before calling `velocity.py` and `backend/ml/features.py` (both hashed research artefacts, left unmodified). `APP_TIMEZONE_OFFSET_MINUTES` (default 330)
exists only for a deployment serving a different single zone.

## 4. Provider support matrix

"Real" means an actual app/bank export parsed on the developer machine
(counts only; no content read into logs or reports). "Synthetic" means a
fixture in `tests/fixtures/statements` or generated by
`tests/statement_pdf_fixtures.py`.

| Provider | Format | Tested with | Parser | Result | Limitations |
|---|---|---|---|---|---|
| PhonePe | PDF | **Real** (2 files, 330 + 651 rows) + synthetic | pdf_generic -> app-block | all rows VALID, directions and times read | the export names payees but prints **no payee UPI ID**: payments cannot be linked to a scanned QR by address |
| Google Pay | PDF | **Real** (1 file, 251 rows) + synthetic | pdf_generic -> gpay-block | all rows VALID, directions and times read | **no payee UPI ID** in the export (the only address printed is the account holder's) |
| Google Pay | CSV | synthetic only | csv_generic | passes fixtures | Format not yet validated - no real GPay CSV export available. The two CSVs in `data/uploaded_statements` are outputs of this project's earlier parser, not provider exports, and were not used as evidence |
| PhonePe | CSV | synthetic only | csv_generic | passes fixtures | Format not yet validated |
| Paytm | CSV / PDF | synthetic CSV only | csv_generic | passes fixture | Format not yet validated; no Paytm PDF tested |
| Bank of Baroda | PDF (account statement) | **Real** (1 file, 60 transactions) + synthetic | providers/bank_of_baroda.py (confidence 1.0: grammar, headers, domain, IFSC) | 60/60 valid, 40 DR / 20 CR from the amount columns, 59 UPI, 30 complete VPAs, 29 VPAs cut by BoB's 49-char narration cap kept as fragments (never matched) | no counterparty names in this format |
| State Bank of India | PDF (account statement) | **Real** (1 file, 17 pages, 415 rows) + synthetic | providers/sbi.py (confidence 0.85: grammar, headers, bank name) | 415/415 valid, 310 DR / 105 CR from the columns, 409 names + bank codes, 0 complete VPAs | SBI prints the counterparty VPA as a fixed 10-character field that never contains a full handle: rows are NAME_ONLY and cannot establish UPI identity; a matching name only yields IDENTITY_UNAVAILABLE |
| Bank statement | CSV | synthetic only | csv_generic | passes fixture (preamble, repeated header, withdrawal/deposit) | Format not yet validated against a real bank |
| Bank statement | PDF (ruled table) | synthetic only | pdf_generic -> table | passes 3-page fixture | Format not yet validated; a table continuing onto a page without its header row is not read |
| Project demo CSV | CSV (`timestamp,counterparty,upi_id,amount,direction`) | real use (the demo) | csv_generic | validated | the only tested format that carries payee UPI IDs |
| Any | scanned/image PDF | - | none (no OCR) | import error | not supported |
